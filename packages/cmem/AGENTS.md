# packages/cmem

Context Memory Engine (CMEM) — opt-in, disabled by default (`cmemEnabled` in settings). Gives providers a persistent cross-session memory: captures an "observation" from every chat turn, compresses it, stores it in SQLite, and later injects relevant past observations back into the request as a synthetic system message. See root `AGENTS.md`'s "Token-saving engines" table and `packages/AGENTS.md`'s directory-map bullet for the one-line summary; this file covers internals.

## Directory map

- `index.js` — barrels only `CmemEngine` from `core/index.js`. Nothing else is re-exported at the root (`Observer`, `Injector`, formatters, `estimateTokens`, etc. must be deep-imported via `package.json`'s `exports` subpaths — `@9router/cmem/capture`, `@9router/cmem/injection`, `@9router/cmem/config`).
- `core/index.js` — `CmemEngine`, the orchestrator. Wires `MemoryStore` + `Summarizer` + `ContextBuilder` + `Observer` + `Injector` together and registers all format-specific injector functions.
- `core/memoryStore.js` — `MemoryStore`: owns the SQLite DDL (`cmem_observations`, `cmem_sessions`, `cmem_context_cache`, `cmem_observations_fts`) and every query (`saveObservation`, `search` — FTS5 when a query string is given, plain `SELECT ... ORDER BY created_at_epoch` otherwise — `getTimeline`, `getObservations`, `deleteObservation`, `clearAllObservations`, `getStats`). Also runs day-based retention `cleanup()` and a process-wide singleton `setInterval` (`_cleanupTimer`, 24h) — guarded by a module-level variable so multiple `MemoryStore` instances don't stack timers.
- `core/summarizer.js` — `Summarizer`: compresses an observation into `{summary, facts, concepts}`. Two paths: `_simpleSummary()` (pure heuristic — first line + first lines as "facts" + top non-stopword tokens as "concepts", zero network calls) used whenever content is short (<100 est. tokens) or `modelEndpoint` isn't set; `_callLLM()` (calls an OpenAI-shaped chat endpoint with a JSON-mode compression prompt) used only when `modelEndpoint` is configured, with a try/catch fallback to `_simpleSummary()`.
- `core/contextBuilder.js` — `ContextBuilder`: assembles the text block CMEM injects. Builds up to three sections (`recent`, `relevant`, `project-facts`), each a list of `{text, tokens}` parts, then greedily fills a `TokenBudget` until it can't fit the next part; returns the joined text plus token accounting.
- `core/tokenBudget.js` — `TokenBudget`: trivial counter (`canFit`/`consume`/`remaining`/`reset`), no dependency on `utils/tokens.js`.
- `core/configResolver.js` — `resolveCmemConfig(userConfig)`: merges user config over `DEFAULT_CMEM_CONFIG`, clamps `tokenBudget` (500–16000) and `maxObservations` (1–100), and falls back to defaults for any `mode`/`historyDepth`/`searchMode` value not in the corresponding allow-list. Pure/sync, no I/O.
- `capture/observer.js` — `Observer`: turns a raw `{model, messages, response, provider}` into a stored-shape observation — pulls the last user message + all `tool` role messages + the response text, strips `<private>...</private>` blocks when `excludePrivateContent`, classifies the turn into one of `capture/types.js`'s `OBSERVATION_TYPES` via keyword regexes, and derives a stable id from `utils/hash.js`.
- `capture/types.js` — `OBSERVATION_TYPES` enum (`decision`, `bugfix`, `implementation`, `exploration`, `review`, `question`, `error`, `change`, `note`).
- `injection/injector.js` — `Injector`: a format→function registry (`registerFormatter`/`inject`); falls back to `_defaultInject` (prepend/unshift a generic system message) for any target format with no registered formatter.
- `injection/formatters/openai.js`, `claude.js`, `gemini.js` — per-provider wire-format injection (see "How CMEM works" below).
- `utils/hash.js` — `hashContent`/`hashObject`: a simple 32-bit rolling hash (not crypto, not collision-resistant) used only to derive observation ids from content, not for security.
- `utils/tokens.js` — `estimateTokens`/`estimateTokensFromMessages`: chars/4 heuristic, no tokenizer dependency.
- `config/defaults.js` — `DEFAULT_CMEM_CONFIG` (mode, tokenBudget, historyDepth, maxObservations, compressionModel, summarizationEnabled, searchMode, contextSections, excludePrivateContent, observationRetentionDays).
- `config/modes.js` — `CMEM_MODES`/`VALID_CMEM_MODE_KEYS`: `code`, `code--zh`, `code--ja`, `code--es`, `code--ko`, `code--fr` — labels only (see Pitfalls; nothing in this package branches on `mode`).

## How CMEM works

Both flows are driven from `open-sse/handlers/chatCore.js` (import at line 36), guarded by `cmemEnabled && db`, per root `AGENTS.md`'s pipeline order: `... → CMEM inject → CMEM capture (post-response)`.

- **Inject** (`chatCore.js:314-325`): builds `new CmemEngine({ enabled: true, config: cmemConfig, db })`, calls `await cmemEngine.init()` (creates tables if missing — see DB section), then `cmemEngine.injectContext(translatedBody, finalFormat)`. Inside, `CmemEngine.injectContext` extracts a query string from the last user message (`_extractQuery`), asks `ContextBuilder.buildContext` for up to `config.tokenBudget` tokens of context, and — if any context was built — calls `Injector.inject(body, contextText, targetFormat)`, which dispatches to the formatter registered for `targetFormat` in the constructor (`openai`/`openai-responses`/`kiro`/`cursor`/`antigravity` → `injectOpenAI`; `claude` → `injectClaude`; `gemini`/`gemini-cli` → `injectGemini`). This mutates `translatedBody` in place before it's sent upstream.
- **Capture** (`chatCore.js:548,553-573`): a **second, separate** `CmemEngine` instance (`cmemCapture`) is built right after the upstream call succeeds, but `.init()` is never called on it — it relies on the inject-side engine (constructed earlier in the same request, `chatCore.js:316-317`) having already run the `CREATE TABLE IF NOT EXISTS` DDL. Once the response resolves, `captureToCmem()` calls `cmemCapture.captureObservation({ model, messages: body.messages||body.input, response: respText, provider })` (skipped if `cmemConfig.observationsEnabled === false`, a flag defined only in `src/lib/db/repos/settingsRepo.js`'s defaults / `packages/validation/cmemSchemas.js` — it is **not** in this package's own `DEFAULT_CMEM_CONFIG`). `captureObservation` runs `Observer.observe()` → `Summarizer.summarize()` → `MemoryStore.saveObservation()`.
- Formatter behavior differs meaningfully per provider: `injectOpenAI` inserts the CMEM block as a new `system`/`developer`-adjacent message right after the last existing system/developer message (or unshifts one if none exists); `injectClaude` appends into `body.system` (string, array, or single object — all three shapes handled); `injectGemini` pushes a `text` part into `body.system_instruction.parts` (or creates one).
- `CmemEngine` also exposes `search`, `getTimeline`, `getObservations`, `deleteObservation`, `clearAllObservations`, `getStats`, `updateConfig` — all pass straight through to `MemoryStore` (or are no-ops when `db` wasn't supplied, since `this.store` is only constructed `if (db)`).

## DB interaction (packages/ → src/lib/db boundary)

Root `AGENTS.md`'s hard rule says `packages/` may not depend on `src/`. `packages/cmem` never violates this literally — **there is no `import` from `src/lib/db` anywhere under `packages/cmem/`**. Instead every caller (`open-sse/handlers/chatCore.js`, and the three route handlers `src/app/api/settings/cmem/{route,search/route,observations/route}.js`) calls `getAdapter()` from `src/lib/db/driver.js` itself and passes the raw adapter object in as `new CmemEngine({ db })`. `core/memoryStore.js` then talks to that object purely through its generic `run/get/all/exec` shape (see `src/lib/db/AGENTS.md`'s "Adapter API surface") — dependency injection, not an import, is the exception mechanism.

The consequence: `MemoryStore.init()` (`core/memoryStore.js:10-72`) contains its **own** copy of the `cmem_observations`/`cmem_sessions`/`cmem_context_cache`/FTS5 DDL, byte-for-byte parallel to `initCmemTables()` in `src/lib/db/repos/cmemRepo.js`. These are two independent schema definitions for the same tables that must be hand-kept in sync. Worse: `initCmemTables()` is **dead code** — it's imported in `src/app/api/settings/cmem/route.js:4` but never called anywhere in the repo (verified via repo-wide grep). `src/lib/db/AGENTS.md`'s pitfall entry claiming "`initCmemTables()` is called lazily from the API route" is stale/inaccurate as of this reading — the real (and only) table-creation path in production is `MemoryStore.init()`, invoked every time a `CmemEngine` is constructed and `.init()`ed. `cmemRepo.js` is also never re-exported from `src/lib/db/index.js`'s barrel, unlike every other repo in that directory.

## Conventions

- ESM only (`type: module` in `package.json`); every file uses `import`/`export`, no CJS.
- `package.json`'s `exports` map (`.`, `./core`, `./capture`, `./injection`, `./config`) documents intended subpath usage but — per `packages/AGENTS.md`'s "Alias resolution" — is not what actually resolves `@9router/cmem/*` imports; the blanket `@9router/*` → `packages/*` jsconfig path does that regardless of `exports`.
- All engine classes are constructed fresh per call site (no singleton/cache) and are fail-open by convention: every public `CmemEngine` method checks `this.enabled`/`this.store` and returns `null`/`[]` rather than throwing when CMEM is off or `db` wasn't supplied.
- New formatters go in `injection/formatters/`, registered in `core/index.js`'s constructor via `injector.registerFormatter(FORMAT_KEY, fn)` — never inline in `injector.js`.

## Pitfalls

| Pitfall | Where |
|---|---|
| `cmem_*` table DDL is duplicated in two places (`MemoryStore.init()` and `cmemRepo.js`'s `initCmemTables()`) with no shared source of truth — and the latter is dead code, never invoked | `packages/cmem/core/memoryStore.js:10-65`, `src/lib/db/repos/cmemRepo.js`, `src/app/api/settings/cmem/route.js:4` |
| Capture-side `CmemEngine` never calls `.init()` — it silently depends on the inject-side `CmemEngine` (a different instance, constructed earlier in the same request) having already created the tables; correctness relies entirely on pipeline order (inject before capture) | `open-sse/handlers/chatCore.js:316-317` vs `:548` |
| Every enabled chat request constructs a brand-new `CmemEngine`/`MemoryStore` for inject, and a second one for capture — `.init()` re-runs 4× `CREATE TABLE IF NOT EXISTS` plus a retention `cleanup()` DELETE query on every request, not once at startup | `open-sse/handlers/chatCore.js:316-317`, `packages/cmem/core/memoryStore.js:67-71` |
| `compressionModel` in `DEFAULT_CMEM_CONFIG` is never wired to `Summarizer`'s `modelEndpoint` — `CmemEngine`'s constructor always does `new Summarizer({})`, so `_callLLM()` is unreachable in production; every observation is summarized by the `_simpleSummary()` heuristic regardless of config | `packages/cmem/core/index.js:29`, `packages/cmem/core/summarizer.js:6-10` |
| `mode` (`code`, `code--zh`, `code--ja`, ...) is validated in `configResolver.js`/`cmemSchemas.js` but nothing in this package reads `config.mode` — the summarization prompt (`COMPRESSION_PROMPT`) is hardcoded English regardless of the selected mode | `packages/cmem/config/modes.js`, `packages/cmem/core/summarizer.js:3` |
| `historyDepth` and `searchMode` are validated/clamped by `configResolver.js` but never consumed — `MemoryStore.search()` always does a global (non-session-scoped) FTS/`ORDER BY` query regardless of either setting; picking `"vector"`/`"hybrid"` `searchMode` or a non-`session` `historyDepth` has no effect | `packages/cmem/core/configResolver.js`, `packages/cmem/core/memoryStore.js:117-143` |
| `utils/hash.js`'s `hashContent` is a plain 32-bit rolling hash, not crypto — two different observations can collide and overwrite each other via `INSERT OR REPLACE` on `id` | `packages/cmem/utils/hash.js`, `packages/cmem/core/memoryStore.js:87-105` |
